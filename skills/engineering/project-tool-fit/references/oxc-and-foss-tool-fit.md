# Oxc and FOSS project-tool fit: research reference

Research date: **2026-11-07**. Purpose: evidence for a future reusable skill that inspects a project, explains useful tools in simple language, and offers a concrete setup. This is a reference, not an instruction to install everything. No tools were installed and no global settings were changed.

## Findings that should shape the skill

- Start with a real problem: slow checks, missed bugs, inconsistent formatting, unused code, browser regressions, inaccessible interactions, or dependency risk. An organization membership, star count, or upstream benchmark is not evidence that a project benefits.
- Oxc includes consumer tools and components for people building tools. Most applications need neither their own parser nor a replacement resolver. Existing Vite/bundler/framework integration may already provide Oxc indirectly. [Oxc introduction](https://oxc.rs/docs/guide/introduction.html)
- Current Oxlint supports JavaScript plugins and type-aware checks. Old advice that it cannot run JS plugins is outdated. Compatibility is still conditional; audit individual rules, processors, parsers, and framework coverage before removing ESLint. [Migration](https://oxc.rs/docs/guide/usage/linter/migrate-from-eslint.html)
- Oxlint handles Vue/Svelte/Astro **script blocks**, not their templates. Oxfmt's formatting support is a different capability and does not prove lint or accessibility coverage. [Linter support](https://oxc.rs/docs/guide/usage/linter.html), [formatter support](https://oxc.rs/docs/guide/usage/formatter/language-support.html)
- Current Oxfmt can format many non-JS formats through native implementations or bundled Prettier. Astro and Svelte require explicit enablement and additional project packages. Do not repeat an old blanket claim that those formats are unsupported. [Language support](https://oxc.rs/docs/guide/usage/formatter/language-support.html)
- Type erasure is not type checking. Oxlint now offers experimental compiler diagnostics, and `tsrs` is a new compiler alternative, but either replacement requires project-specific parity checks. Neither a transform nor lint-rule coverage proves compatibility with the project's compiler, declaration build, or framework checker. [Type-aware linting](https://oxc.rs/docs/guide/usage/linter/type-aware), [config reference](https://oxc.rs/docs/guide/usage/linter/config-file-reference.html), [tsrs compatibility](https://github.com/oxc-project/tsrs/blob/main/docs/COMPATIBILITY.md)

## Inventory method and coverage

Queried the public GitHub organization API using `type=all&per_page=100&page=N`. Page 1 returned **68 repositories**, fewer than the page size, so pagination terminated with all 68 returned public repositories classified below. The loop advanced only when a page contained 100 items. A redundant page-2 request later hit GitHub's unauthenticated rate limit; that error is **not** evidence of an empty page. No private repositories are claimed. [Inventory endpoint, page 1](https://api.github.com/orgs/oxc-project/repos?type=all&per_page=100&page=1), [GitHub pagination contract](https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api)

The API supplied `archived`, `fork`, license detection, description, and `pushed_at`. Classifications below are research judgments, using repository descriptions and READMEs. A GitHub `fork=false` flag does not mean source is original: several explicitly describe themselves as forks. An absent license or `NOASSERTION` means **unverified**, not public domain. Source manifests override coarse license detection where checked. A recent push is an activity signal, not proof of release quality or an SLA.

### ESLint, frameworks, accessibility and compiler overlap

1. **Build a rule coverage map from the repository.** Include native ESLint rules, typescript-eslint semantic rules, custom JS plugins, processors, custom parsers, ignores, overrides, globals and monorepo config boundaries. Oxlint's JS plugin system covers much of the ESLint v9 API, not every plugin or parser ecosystem. Retain ESLint for concrete gaps. `eslint-plugin-oxlint` can disable duplicated rules, but its existence does not prove the Oxlint run enables an equivalent rule with equivalent options. [JS plugin migration](https://oxc.rs/docs/guide/usage/linter/migrate-from-eslint.html), [overlap adapter](https://github.com/oxc-project/eslint-plugin-oxlint)
2. **Separate template analysis from script analysis.** `.vue`, `.svelte`, `.astro` script extraction leaves template rules and cross-template symbol usage outside equivalent coverage. Some rules deliberately ignore framework files: `typescript/consistent-type-imports` is one documented example because template uses cannot be determined. Keep framework-specific lint/check tools wherever required. Verify individual jsx-a11y rules for React/JSX; do not assume they cover framework templates or all accessibility issues. [Supported files](https://oxc.rs/docs/guide/usage/linter.html), [specific rule limitation](https://oxc.rs/docs/guide/usage/linter/rules/typescript/consistent-type-imports)
3. **Keep runtime accessibility testing and human review.** Static JSX/template rules cannot see all rendered states, CSS contrast, focus behavior or keyboard interactions. axe returns structured violations and separate incomplete/review findings; an empty violations list is not a compliance certificate. [axe API](https://github.com/dequelabs/axe-core/blob/develop/doc/API.md)
4. **Do not remove `tsc` mechanically.** Current docs explicitly offer `oxlint --type-aware --type-check` as a possible replacement for a separate `tsc --noEmit` CI step; the config reference calls type checking experimental. Demonstrate matching diagnostics for the project's pinned compiler/config/file discovery first. Lint diagnostics do not replace declaration emit, JS emit, build/reference semantics or framework template type checking. Keep the existing compiler path for any needed capabilities until verified. [Type-aware guide](https://oxc.rs/docs/guide/usage/linter/type-aware), [experimental config](https://oxc.rs/docs/guide/usage/linter/config-file-reference.html), [isolated declarations](https://oxc.rs/docs/guide/usage/transformer/isolated-declarations.html)

### Prettier, Tailwind and formatting ownership

Oxfmt migration reads supported Prettier configs, migrates ignores/overrides and compatible options, and warns about unsupported plugins. YAML/JSON5/TOML Prettier config formats need conversion first. It migrates options for the Tailwind, Svelte, Astro and package.json integrations into built-ins; arbitrary Prettier plugins are not automatically supported. The migration sets an unspecified print width to 80 to preserve Prettier's default. [Migration contract](https://oxc.rs/docs/guide/usage/formatter/migrate-from-prettier.html)

Current language docs require `svelte` plus enabled `svelte` formatting, and `@astrojs/compiler-rs` plus enabled `astro` formatting. Tailwind sorting is opt-in (`sortTailwindcss`, default disabled), uses the Tailwind plugin's algorithm, and changes option names. Inspect Tailwind version/config or stylesheet discovery, custom functions, class attributes and template examples rather than assuming identical output. [Language requirements](https://oxc.rs/docs/guide/usage/formatter/language-support.html), [options](https://oxc.rs/docs/guide/usage/formatter/config-file-reference.html)

Choose one formatter owner per file type. Run a reviewed sample diff covering templates, Tailwind classes, MDX, generated files and plugin-dependent formats before a whole-repository rewrite. Preserve an existing Prettier pipeline when its plugin coverage is needed. Treat import sorting as a potentially behavioral change, especially around side-effect imports. `sort-package-json` explicitly documents different ordering from the original npm tool. [Sorting implementation](https://github.com/oxc-project/sort-package-json)

**webpack:** `oxc-webpack-loader` 1.0.2 (July 2, MIT) wraps `oxc-transform` and describes itself as a replacement for Babel/SWC loaders. That label does not establish Babel plugin compatibility: audit required transforms, targets and source maps before swapping. `oxc-webpack-plugin` 0.3.0 (May 27, MIT) minifies JS assets. Its README instructs replacing the default minimizer and documents legal-comment extraction; do not accidentally run multiple JS minimizers or drop required notices. Neither is a reason to introduce webpack into a project using another bundler. [Loader README/releases](https://github.com/oxc-project/oxc-webpack-loader), [minifier plugin README/releases](https://github.com/oxc-project/oxc-webpack-plugin)

**Editors:** official repositories exist for [VS Code](https://github.com/oxc-project/oxc-vscode), [JetBrains](https://github.com/oxc-project/oxc-intellij-plugin), [Zed](https://github.com/oxc-project/oxc-zed) and [coc.nvim](https://github.com/oxc-project/coc-oxc). All API license detections are MIT; Oct/Nov 2026 pushes were observed. Exact extension releases, marketplace publisher signatures and all per-editor feature matrices were not checked. Match the user's editor, project-local CLI/config and save actions; do not claim all extensions have identical formatting/linting capabilities. The coc README explicitly lists both Oxlint and Oxfmt. Keep one formatting save action per file type.

**CI wrappers:** the lint/format Actions and pre-commit mirrors are integrations, not new analyzers. Exact wrapper release versions and licenses were not established. Prefer existing package scripts and locked local dependencies when sufficient; if an Action is needed, inspect its source, permissions and pinned revision first. Do not recommend internal setup/release/security Actions merely because they live in this organization.

## Decision rubric for the future skill

1. **Inspect before recommending.** Read languages/file types, manifests, lockfiles, workspaces, scripts, CI, existing config, editor choices and documented standards. Use structural code tools where appropriate; do not infer a whole stack from one extension or package. Identify generated/vendor files and published library entry points.
2. **Name the pain and baseline.** “Checks take four minutes,” “template accessibility rules are missing,” or “unused dependencies complicate upgrades.” If no problem is established, retaining the current tool is a valid result. Measure on this project's representative checks when speed is the claimed benefit.
3. **Create a small coverage/overlap map.** Existing responsibility → candidate capability → gaps → retained owner. Distinguish syntax lint, semantic lint, compiler checking, templates, formatting, browser tests and rendered accessibility. Avoid two conflicting formatters and silently disabled rules.
4. **Apply hard fit gates.** Required languages/plugins/runtime/OS/architecture, license obligations, maintenance/release quality, config/ignore parity, offline/network requirements and build semantics. A failed required capability means keep the existing tool or bound a pilot, not advertise a replacement.
5. **Give a short ranked answer.** Prefer at most a few recommendations: adopt, pilot, keep, or skip. For each: a concrete project fact, plain-language benefit, overlap/gap, evidence confidence and setup scope. Example: “Keep ESLint for Vue template rules. Pilot Oxlint for shared TS files because lint time is the slow gate.” Avoid benchmark multipliers without a project measurement.
6. **Offer concrete setup.** Name dependency/script/config/editor/CI files that would change, expected gate commands, preserved checks and rollback. Use the existing package manager and local dependencies. An assessment-only request does not authorize installing tools, global changes or migrating every file. When setup is requested, make the smallest reviewable change and run the relevant checks.
7. **Verify behavior and stop.** Compare before/after diagnostics and representative formatting, build/declaration output where applicable, test behavior and measured runtime. Keep source edits separate from bulk formatting where practical. Report skipped checks, unverified evidence and remaining limitations. No tool catalog expansion after the identified need is met.

## Evidence limits and refresh instructions

- Coverage is **68/68 public repositories returned by the paginated API**, not private organization inventory. No source mirror or downloaded raw-response artifact was persisted; the API query and classified snapshot above are the audit record. The redundant page-2/release-list requests were rate-limited after the successful first inventory and per-repository metadata queries.
- Library docs were resolved and queried through Context7 (Oxc, Knip, Biome, ESLint, Prettier, TypeScript, Vitest, Playwright, axe, Ruff and uv); citations link to the owning docs/source returned. Context7 can index older material: specific current framework support and experimental labels were retained rather than extrapolating historical snippets. No runtime installation validated those docs locally.
- Exact releases of editor extensions, migration/overlap adapters, CI wrappers and several specialized parser libraries were not established. Some source manifest versions differ from npm packages. Refresh the selected package's release, manifest, changelog and license at implementation time.
- Inventory licenses for internal/test repos with missing detection are explicitly unknown. No exhaustive license audit of vendored/transitive code or build artifacts was performed. `oxc-node` declares MIT in Cargo but a root LICENSE was not located. `oxc-index-vec` has differing API/repository-package signals; inspect actual distributed notices. Artwork is noncommercial CC, not FOSS software.
- No blanket maturity promise was established for every Oxc library, and formal current Oxfmt alpha/beta wording was not established. Pre-1.0 versions are reported without inventing a release label. tsrs explicitly remains on a path toward a stable TS 7.1-compatible release.
- This research did not benchmark a target project, test every supported rule/formatter language, validate emitted code/source maps, install editor extensions, exercise CI wrappers, or prove full a11y/security coverage. Those are project-specific checks, not missing reasons to install more tools.

The future skill should keep this reference as dated evidence, refresh only the candidates needed by the project, and clearly mark unavailable evidence instead of filling gaps with guesses.
